What it does not do

It reads an undocumented endpoint

The same one Claude Code uses internally. Anthropic can change or remove it at any time, and the consumer terms restrict automated access, so whether a read-only status check sits inside them is unclear. Worth knowing before you install it.

It consumes nothing. No prompts, no output, no tokens. The request asks for a number and receives a number.

It bypasses nothing. Every figure it shows is already available in /usage and on the settings page. It changes where you see them, not what they are.

It stays on your machine. A shell script, no server, no telemetry, no account. One request to Anthropic's own API using a token already in your Keychain.

Devblog · Friday 7 August 2026

Three versions in one day

Built a menu bar meter for Claude usage limits, shipped it, and learned that the obvious explanation for a bug is usually the wrong one.

Where it started

Claude runs on two limits, a five hour session window and a seven day window. Checking either meant opening a browser tab, and I was doing that several times a day, usually right before starting something long. The reference point was iStat Menus. CPU and temperature sit in the corner of the screen and you absorb them without asking. That is the right shape for a number you want to be aware of.

Finding the number

The hard part was not display, it was access. Nothing published exposes subscription usage. Signing into Claude in a browser or the desktop app leaves nothing behind on the machine, so there was nothing to read.

Claude Code is different. It stores a token in the macOS Keychain. Once that was clear, everything else followed: read the token, ask for the numbers, draw them. v1 was working inside an hour, showing both meters with progress bars, reset countdowns and colour thresholds.

Making it speak

A meter you have to look at is half a tool. v2 added notifications at a threshold you choose, the plan name pulled from the stored credentials, a history graph, and a settings menu so nothing needed a text editor. It also cached the last good reading, so a failed request greyed the numbers out instead of blanking them.

The rate limit, and the wrong answer

Then it started refusing to load. HTTP 429. Rate limited.

The obvious read was that v2 had got greedy, and the obvious fix was a slower timer. Both wrong. v1 and v2 make exactly one request per run. Nothing had changed about how often it asked.

What changed was me. I had spent ten minutes swapping files, clicking refresh, and opening the settings menu, and every settings click forced an immediate re-fetch. Twenty odd requests in a few minutes will trip a limit that one per minute never touches. The tool was not the problem, the person testing it was.

So the fix was not a slower schedule, it was a cache. v3 holds responses for two minutes and serves everything inside that window from memory. Menu clicks, manual refreshes and restarts now cost nothing. Only the timer reaches the network. Same pass also flattened the escalating backoff into a single fifteen minute pause, made the plan name permanent, and collapsed three near identical meter blocks into one function, taking about ninety lines out while doing more.

Things that cost more time than they should have

  • Files arrive on a Mac without permission to run. Hit that wall at least once per version before the installer started handling it.
  • SwiftBar has no slider, so the notification threshold became a submenu of preset values. Faster to use anyway.
  • An option to hide the icon when idle worked perfectly, including hiding the menu you would use to turn it back off. It needed a command line escape hatch before it could ship.
  • Notifications arrive attributed to Script Editor, because shell scripts raise them through the macOS scripting bridge. Not fixable from a plugin, so it went in the README instead.

What I would tell myself at the start

When a bug appears alongside a new version, check whether the version actually caused it before you start changing the version. I nearly shipped a slower refresh interval that would have made the tool worse and fixed nothing.

Next

Windows is the obvious ask, but it is a rewrite rather than a port, since the whole thing hinges on the macOS Keychain. An iPhone widget is possible but needs a relay from a Mac that stays awake, which is a poor deal for anyone but me. For now v3 does what I wanted on the day I wanted it.

Building a payment gateway

Roughly 4,200 lines of TypeScript and SQL in a day. A double-entry ledger, a transaction monitoring engine, settlement controls, and an operations console. This is what got decided, what broke, and what I’d do differently.

The three constraints

Every structural decision came out of these.

Everything must be provable after the fact. Who approved this payout. What the structuring threshold was in March. Why this alert was closed. So the ledger, audit log and compliance tables are append-only at the database level, not by convention. Someone with application access cannot rewrite history.

Money and state must move together. A payment marked succeeded without its ledger postings, or postings without the payment, is a reconciliation break you may never fully resolve. Every capture commits the status change and the accounting in one transaction.

Controls that depend on discipline fail. Maker-checker on payouts is a CHECK constraint, not a code path someone routes around at 2am.

The ledger

Double-entry, integer minor units, balances derived from postings.

Money is integers

No floats. No decimal library. Every amount arrives from an API or a rail statement as an integer and leaves as one. A decimal type only creates places where rounding can hide.

export function assertMinor(value: unknown, field = 'amount'): asserts value is Minor {
  if (typeof value !== 'number' || !Number.isInteger(value)) {
    throw new TypeError(`${field} must be an integer in minor units`);
  }
}

The one genuinely tricky function is splitting an amount without losing centavos:

export function allocate(amount: Minor, weights: number[]): Minor[] {
  const total = weights.reduce((a, b) => a + b, 0);
  const parts = weights.map((w) => Math.floor((amount * w) / total));
  let remainder = amount - parts.reduce((a, b) => a + b, 0);
  for (let i = 0; remainder > 0; i = (i + 1) % parts.length) {
    parts[i] += 1;
    remainder -= 1;
  }
  return parts;
}

Floor everything, then distribute the remainder one centavo at a time. Tested across a range of amounts and weight sets: the parts always sum back to the original.

Balances are derived, never stored

The temptation to add a balance column is strong. It's one query instead of an aggregate, and the aggregate gets slower as postings grow.

Resist it anyway. A cached balance is a second source of truth, and the two will disagree at the worst possible moment. If reads get slow, the answer is a materialised view you rebuild from postings, not a column you mutate.

CREATE VIEW account_balances AS
SELECT a.id, a.code, a.type,
  CASE
    WHEN a.type IN ('asset','expense')
      THEN COALESCE(SUM(CASE WHEN p.direction='debit' THEN p.amount_minor ELSE -p.amount_minor END), 0)
    ELSE  COALESCE(SUM(CASE WHEN p.direction='credit' THEN p.amount_minor ELSE -p.amount_minor END), 0)
  END AS balance_minor
FROM accounts a LEFT JOIN postings p ON p.account_id = a.id
GROUP BY a.id;

Immutability enforced by the database

CREATE OR REPLACE FUNCTION forbid_mutation() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'Table % is append-only', TG_TABLE_NAME;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER postings_immutable
  BEFORE UPDATE OR DELETE ON postings
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

Corrections are reversing entries. The original stays. What you believed and when survives intact.

The balance check is deferred

This one bit me later, so it's worth showing:

CREATE CONSTRAINT TRIGGER postings_balanced
  AFTER INSERT ON postings
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION assert_entry_balanced();

Deferred means it evaluates at COMMIT, once every leg of an entry exists. Without that, you couldn't insert a two-leg entry at all — the trigger would fire after the first leg and see debits without credits.

Two decisions worth explaining.

Reserve is a liability, not revenue. It's the merchant's money we're holding. Booking it as income flatters the P&L and leaves you unable to fund the release when the hold expires.

Suspense exists at all. Money that arrives and can't be matched goes there and stays until a human resolves it. Never let an unmatched credit flow into a merchant balance on the assumption it'll sort itself out. A growing suspense balance means reconciliation is falling behind.

Posting recipes

Every money movement goes through one function, so there's exactly one place to audit the accounting:

Dr  rail clearing        gross
  Cr  merchant payable     net
  Cr  merchant reserve     reserve
  Cr  fee revenue          fee

Plus postRefund, postChargeback, postReserveRelease, postPayoutSettled, postToSuspense.

The chargeback recipe surfaces shortfall explicitly rather than letting a merchant account go quietly negative:

const fromMerchant = Math.min(amountMinor, Math.max(availablePayableMinor, 0));
const shortfall = amountMinor - fromMerchant;
// shortfall hits expense:chargeback — the platform absorbs it, visibly

Transaction monitoring

Ten rules. Two design decisions matter more than the rules themselves.

Rules are data, not code

Thresholds live in a table:

INSERT INTO aml_rules (code, name, severity, params) VALUES
  ('STRUCTURING', 'Deposits clustered below threshold', 90,
   '{"threshold_minor": 500000000, "floor_pct": 80, "count": 3, "window_hours": 24}');

Not for flexibility. Because the parameter set in force on any given date has to be recoverable. Change them through migrations, never by hand.

Nothing auto-blocks

Rules raise alerts; a human decides. Auto-blocking looks responsible and is worse in practice, because it trains operators to disable rules that create friction.

One exception, and it's categorical rather than a threshold: a payer outside the licensed jurisdiction fails outright. For a geo-fenced licence that's a perimeter breach, not a risk score — they shouldn't have been able to transact at all.

Screening runs twice

Pre-authorisation, before the payer is sent to the rail. Catches what's knowable then: geography, velocity, structuring patterns.

Post-settlement, on the callback, because that's the first moment the funding instrument holder name exists. NAME_MISMATCH and SHARED_INSTRUMENT can't be evaluated any earlier.

The name matching problem

The most interesting small problem of the day.

Exact string equality would flag most legitimate payments here. Filipino names carry middle names, maternal surnames and suffixes that appear inconsistently across ID documents and bank records. "Juan Cruz" versus "Juan Miguel Santos Cruz" is the same person and would fail.

Token similarity, weighted toward the smaller set:

export function nameSimilarity(a: string, b: string): number {
  const norm = (s: string) =>
    s.toLowerCase()
      .normalize('NFD').replace(/[\u0300-\u036f]/g, '')
      .replace(/\b(jr|sr|ii|iii|iv)\b\.?/g, '')
      .replace(/[^a-z\s]/g, ' ')
      .split(/\s+/).filter((t) => t.length > 1);

  const ta = new Set(norm(a));
  const tb = new Set(norm(b));
  let shared = 0;
  for (const t of ta) if (tb.has(t)) shared += 1;
  return shared / Math.min(ta.size, tb.size);
}

Dividing by the smaller set is the whole trick. Plain Jaccard would penalise the longer name for having extra tokens.

An alert everyone ignores is worse than no alert, and this is the rule most likely to generate them.

A broken rule must not break payments

try {
  const hit = await fn(client, ctx, rule.params);
  if (hit) alerts.push({ ruleCode: rule.code, severity: rule.severity, detail: hit.detail });
} catch (err) {
  alerts.push({
    ruleCode: rule.code, severity: 100,
    detail: { rule_error: String(err), action_required: 'Rule failed to evaluate' },
  });
}

The failure becomes a maximum-severity alert. Silent rule failure is how monitoring quietly stops working.

Controls in the schema

Maker-checker

CONSTRAINT payout_maker_checker CHECK (approved_by IS NULL OR approved_by <> created_by)

Four words in a table definition. Cannot be bypassed by a new code path, a refactor, or someone in a hurry.

Idempotency

Enforced by a unique index, not check-then-insert:

UNIQUE (merchant_id, idempotency_key)

Under concurrency, check-then-insert produces duplicate charges. Fastest way to lose a merchant's trust.

Confirmation is row-locked

SELECT p.*, m.fee_bps FROM payments p JOIN merchants m ON m.id = p.merchant_id
WHERE p.rail = $1 AND p.rail_reference = $2
FOR UPDATE OF p

Rails retry callbacks. Without the lock, two concurrent retries both capture.

Things that broke

The seed script that wouldn't seed

Best error of the day.

severity: 'ERROR'
where: 'PL/pgSQL function assert_entry_balanced() line 13 at RAISE'

The balance check is DEFERRABLE INITIALLY DEFERRED — it evaluates at COMMIT. But the seed script inserted each posting on its own autocommit, so the trigger fired after the first leg, when debits were 100 and credits were 0.

Fix was one BEGIN and one COMMIT around the leg inserts.

Twenty minutes of annoyance, then a useful realisation: the protection working correctly looked exactly like a bug. If the balance check hadn't existed, the demo data would have loaded fine and the book would have been silently wrong.

Background jobs burying the real error

The database was unreachable. The API started anyway, and the webhook worker began this every five seconds:

{"level":50,"msg":"webhook delivery failed","e":{"code":"ECONNREFUSED"}}

Endlessly, scrolling the actual cause off screen.

try {
  await pool.query('SELECT 1');
  app.log.info('database reachable');
} catch (err) {
  app.log.fatal({ err }, 'cannot reach database, refusing to start');
  process.exit(1);
}

A gateway that starts without its ledger looks healthy to a load balancer while being unable to record a single peso. Worse than not starting.

Password echoing to the terminal

readline.question doesn't mask input. The password appeared in plain text in the scrollback and, on one attempt, ended up in shell history.

Fixed with raw-mode stdin:

const password = await new Promise((resolve) => {
  stdout.write('Password (min 12 chars): ');
  stdin.setRawMode?.(true);
  let buf = '';
  const onData = (ch) => {
    const s = ch.toString('utf8');
    if (s === '\n' || s === '\r') { /* finish */ }
    else if (s === '\u0003') process.exit(1);
    else if (s === '\u007f') buf = buf.slice(0, -1);
    else buf += s;
  };
  stdin.on('data', onData);
});

The HMAC scheme is broken

Still open, and it's a design error rather than a typo.

The merchant API signs requests: HMAC-SHA256(secret, METHOD \n PATH \n TIMESTAMP \n sha256(body)). Sound scheme.

But I stored the secret as an argon2 hash. Correct for passwords, wrong here — the server needs the actual secret to recompute the signature, and an argon2 hash is one-way by design.

As written, verification cannot work. It needs either an encrypted-at-rest secret (KMS-wrapped) or a separate keyed verifier.

Logged, not papered over. Better a known-broken component with a comment on it than a quietly wrong one.

The console

React, Vite, no component library. Nine screens reading live from the database.

Design brief: control room, not marketing page. Dense, dark, monospaced tabular figures so a wrong digit is visible without reading. Severity carried by a left border rule rather than a background fill, so a screen full of alerts stays legible.

Three interactions that make the argument better than documentation:

Clearing an alert requires a note of at least ten characters. Server-side, not a UI hint:

if (!note || note.trim().length < 10) {
  return reply.code(422).send({
    error: 'note_required',
    message: 'Explain why this alert is not suspicious, in at least 10 characters.',
  });
}

An alert cleared without a reason is indistinguishable from an alert nobody looked at.

"Approve as preparer" is a real button that fails. The rejection comes from the database constraint, not the interface. Worth demonstrating, because it proves there's no path around it.

Opening a case blocks that merchant's settlement, visible immediately on the payouts screen.

Shadow mode

The rescan endpoint runs the current rule set over historical payments:

app.post('/internal/rescan', async (req) => {
  const { hours = 168 } = req.body;
  // delete un-cased alerts, re-evaluate, re-persist
  return { scanned, alerts_created };
});

Change a threshold, rescan, see what the new configuration would have caught before putting a human on the queue. Also how you measure a false positive rate, which is the number deciding whether a rule is usable at all.

The demo seed plants four patterns deliberately, so rules can be seen firing on data that wasn't hand-picked for them: a structuring run, a threshold breach, a third-party funder, and one device across six accounts.

Ledger integrity as a health check

app.get('/internal/ledger-check', async (_req, reply) => {
  const result = await assertLedgerBalanced(pool);
  return reply.code(result.ok ? 200 : 500).send(result);
});

Total debits minus total credits across the whole book. Must be zero.

Wired into three places: the health endpoint, a five-minute background job that logs fatal on drift, and CI. The CI one is the most valuable line in the pipeline — if the book doesn't balance there, it won't balance in production either.

- name: Ledger integrity
  run: |
    npm run seed
    node -e "/* SUM(debit) - SUM(credit) must be 0 */"

Setup friction, and fixing it

First run took an hour, most of it environment problems: wrong working directory, Docker not installed, Postgres not on PATH, the seed bug above.

None of it interesting, all of it recurring on every new machine. So it became a script that checks state rather than assuming it:

./start.sh

Postgres running? Start it. Database exists? Create it. .env present? Generate one with real secrets. Dependencies current? Install. Migrations pending? Run them. Database empty? Seed it. Ports occupied? Free them. Then start both processes, verify the ledger balances, open the browser.

Idempotent throughout. Safe to run when everything is already up.

Two companions: stop.sh and reset.sh (wipes the database, asks first).

What I'd tell someone starting this

Build the ledger first and get it right. It's the layer you cannot fix later. Everything else is replaceable.

Put controls in the schema. A control enforced by application code is a control someone routes around under deadline pressure. A CHECK constraint isn't.

Derive, don't store. Any number you cache is a number that can drift from its source.

A protection working correctly can look exactly like a bug. Sit with the error before weakening the constraint.

Make failure loud. Silent rule failures, silent job retries, and quiet startup without a database are all worse than a crash.

Write down why a threshold is what it is. Five minutes now, versus "I don't remember" later.

Open items

  2. Calibrate the rules. Shadow mode over real volume, measure false positives per rule, tune before anyone works the queue.
  3. One real rail adapter to replace a mock.
  4. Property tests on the posting recipes. Currently only allocate is properly covered.
  5. Materialised balances if the aggregate gets slow. Rebuild-from-postings, never a mutable column.
