What it does

Six things, and the first one is the reason the other five can be trusted.

A ledger that cannot drift

Double entry, integer centavos, balances computed from postings on every read. No cached balance column, because a cached balance is a second source of truth and the two eventually disagree.

Nothing can be edited

Postings, journal entries, audit log and case notes reject UPDATE and DELETE at the database. Corrections are reversing entries. What you believed, and when, survives.

Ten monitoring rules

Structuring, third-party funding, shared devices, velocity, dormant reactivation. They raise alerts. A human decides. Nothing auto-blocks except a payer outside the licensed area, which is a boundary rather than a score.

Two signatures on money

The person who prepares a payout cannot approve it. That is a CHECK constraint, so there is no code path around it, including for whoever is in a hurry at 2am.

Reconciliation that names the bad case

Statement lines match, mismatch, or go unmatched. The dangerous one is the fourth: a payment we think succeeded that the provider never reported. It gets its own count.

Shadow mode

Change a threshold, rescan the last week, see what the new configuration would have caught. That is how you measure a false positive rate before putting a person on the queue.

How it came together

In order, because each part only made sense once the one before it existed.

LedgerFirst

The part you cannot fix later

Everything else is replaceable. The ledger is not, so it went first and took the longest per line.

Money is integers throughout. The only genuinely tricky function splits an amount across parts without losing a centavo: floor everything, then hand the remainder out one centavo at a time.

RulesThen

Data, not code

Thresholds live in a table. Not for flexibility, but so the numbers in force on any given date can be recovered afterwards.

The hardest small problem was name matching. Exact comparison flags most legitimate Filipino payments, because middle names and maternal surnames appear inconsistently across documents. Token overlap divided by the smaller name solves it: Juan Cruz against Juan Miguel Santos Cruz scores 1.0 instead of failing.

ControlsThen

Put it in the schema

A control enforced by application code is a control someone routes around under pressure. So maker-checker is a constraint, merchant activation is a trigger, and idempotency is a unique index rather than a check-then-insert that produces duplicate charges under load.

ConsoleLast

A control room, not a dashboard

Dense, dark, monospaced figures so a wrong digit is visible without reading it. Severity is a border, not a fill, so a full screen of alerts stays legible.

One deliberate friction: clearing an alert requires a written reason, and the server rejects anything under ten characters. An alert cleared without a reason is indistinguishable from an alert nobody looked at.

The bug that was not a bug

The best twenty minutes of the build.

Loading demo data failed and would not stop failing: 

severity: 'ERROR'
where: 'PL/pgSQL function assert_entry_balanced() line 13 at RAISE'

The balance check is a deferred constraint. It evaluates at commit, once both sides of an entry exist. The seed script was inserting each side on its own autocommit, so the trigger fired after the first one and saw a debit with no matching credit.

The fix was two words: 

await c.query('BEGIN');
// ... insert every leg of the entry ...
await c.query('COMMIT');

Then the useful part. The protection working correctly looked exactly like a broken build. If that constraint had not been there, the data would have loaded without complaint and the books would have been quietly wrong.

Which is the whole argument for putting rules in the database instead of in the code that writes to it. Worth sitting with an error for a while before deciding the constraint is the problem.

Straight answers

What it is not, and why there is no download button.

It is not authorised, and running it would not change that

Processing payments for other businesses is a licensed activity. This has none of the registrations that would require. Hosting a thing does not make it permitted.

It has never touched real money

Every provider is a mock. There is no bank relationship. Every figure you would see in the console came from a seed script.

The rules are calibrated against nothing

The thresholds are starting values. They need to run in shadow mode against real volume before anyone works the queue. An alert queue nobody can clear is worse than no queue: it is documented evidence you saw something and did nothing.

One component is knowingly broken

The request signing stores the shared secret as a one-way hash, which makes the signature impossible to recompute. It cannot work as written. It is marked in the source rather than quietly patched over, because a known-broken component is safer than a confidently wrong one.

The repo is private and staying that way

It encodes the control design and the monitoring thresholds. That is not useful to publish, and everything worth sharing is on this page.
